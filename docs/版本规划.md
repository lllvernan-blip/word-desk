# 单词翻译练习台 · 版本规划（1.0 / 2.0）

> 基线：`dist/` 当前发布源（`app.js` 4557 行 / `index.html` 551 行 / `styles.css` 2353 行 / `sw.js` v47），审阅日期 2026-11-06。
> 本文所有【事实】均来自代码、数据文件或已有审查报告；【判断/建议】是推断，可被后续数据推翻。
> 没有真实用户留存数据，凡涉及留存、转化、活跃的结论一律标注「暂无数据，需先埋点观察」。

## 0. 结论先行

1. **1.0 不是"再加功能"，是补外壳**：5 个已知缺陷合计约 0.5～1 人日，但缺失的是首次引导、备份恢复、隐私说明、可见版本与更新提示——这些决定"陌生人会不会在 10 分钟内退出"。
2. **1.0 最大的一颗雷是数据只进不出**：现在只有"导出给作者看"，没有恢复入口，也不含自建词。用户换机或清缓存即永久清零，而且不会回来。
3. **2.0 推荐走 B（学习效果）**，不建议 A（内容深度）和 C（平台化）。理由见第 3 节；A 只在出现"内容不够用"的真实信号后局部做，C 需要后端与运维，单人维护下失败概率最高。

## 1. 现状评估

### 1.1 它现在是什么

**一句话**：一个"先按前后缀/词根筛出一批词，再走拆解→猜义→验证→拼写"的、自带 3400 词与 100% 离线发音、数据只存本机的静态 PWA 练习工具。

（【事实】筛词是入口，四阶段是主体，3400 词与音频包随包下发，无账号无后端。）

### 1.2 已经强在哪三点

1. **练习闭环的数据底座是完整的**（【事实】）
   - 内置 3400 词 = 400 精选 + 3000 ECDICT 核心，交集 0；词条含释义、词性、前后缀、音标。
   - 离线音频覆盖 3400/3400，17 个分片 + `index.json`（约 14.6 MB），`index.words` 每条带 `[pack, offset, length]`；前端按词 Range 取片、支持"整包 200 / 206 带 Content-Range / 206 无 Content-Range"三分支切片，播过的词按 `wtp-audio-v{index.v}` 缓存且可清理。
   - 三种方向（英译中 / 中译英 / 听音拼写）、四阶段，听音只对索引里真实存在的词开放，无音频降级为看音标/字母提示，**不再调用系统朗读**。
2. **原始核心需求（按词缀筛词再练）做得最深**（【事实】）
   - 前缀 / 后缀 / 词根三组分类筛选 + 关键词 / 词性 / 首字母 + 选中条件摘要，筛选结果可直接开练；词库页同样支持筛选、编辑、新增、导入。
   - 导入 6 个入口：AI 提示词、文件拖拽（CSV/TXT/JSON）、粘贴临时练习、CSV 模板、JSON 示例、示例词表；导入后给出"多少词有离线音频、多少走系统朗读"的统计。
3. **工程自洽度高于一般个人项目**（【事实】）
   - SW 分层：页面/`app.js`/`styles.css`/`content/` 网络优先（避免长期停在旧脚本），静态资源缓存优先后台更新，音频 Range 请求直通、`audio/index.json` 网络优先（防止旧索引配新分片）。
   - IndexedDB（`wtp.db.v3`）打开失败降级 localStorage / 内存；播放态在 `blur`/`pagehide`/`visibilitychange`/`pointercancel` + 8 秒兜底复位。
   - 内容治理：29 词标记、5 词剔除（ass / bloody / rape / sex / sexual），四选一干扰项只从安全池取；用户可「别出现」并撤销。
   - 390px 无横向溢出、输入框 16px 防 iOS 聚焦缩放、PWA 可安装、离线可用（需先在线加载一次）。

### 1.3 弱在哪三点

1. **只有练习引擎，没有产品外壳**（【事实】）
   - 无首次引导、无帮助页、无隐私说明页、无"新版本已更新"提示；初始化失败只在页面底部贴一张"初始化失败"卡片。
   - 新用户第一次打开，看到的是「待复习 0 / 新词 10 / 今日已练 0 / 连续 0 天」四格数字、一个「用今日复习计划（10 词）开始练习」按钮，以及一行"选词，然后做中英互译"。没有任何文字解释四阶段、"别出现"、复习算法或数据存哪里。
   - 版本号不可信：footer 硬编码 `V0.09`，`CONFIG.version` 是 `2026.11.05.2`（只进埋点，不展示）。
   - 词根专项有实现但入口永远不可见：`index.html` 里 `<details id="rootDrill" hidden>`，`app.js` 只给它绑事件、从没有任何一处移除 `hidden`。
2. **数据只进不出**（【事实】）
   - 导出只有一个「导出进度」按钮，payload 是 `stats / daily / 4 项 settings / summary / wrongBook / srs`，**不含自建词（userWords）、不含屏蔽表（blocked）**；没有导入/恢复入口，没有"清除全部数据"入口。
   - 导出文案写的是"发给作者就能看你的使用数据"——它现在被当反馈通道用，不是备份。
3. **内容深度与算法都停在"能跑"**（【事实】）
   - 词根数据只覆盖 119 词 / 74 个词根，family ≥ 4 词的只有 4 个；叠加上一条的入口隐藏，专项训练实际不可用。
   - 复习算法是自实现简化 FSRS：`RETENTION=0.9`、`MAX_IVL=365`、`INIT_S=[0.4,1.18,3.17,15.69]`、`INIT_D=7.19` 全部硬编码，未用真实复习数据拟合；每日新词 10（上限 15）、复习上限 120。
   - 无例句、无搭配、无同义/反义网络；发音评分（跟读）已下架（`FEATURES.followRead=false`），代码保留但永久关闭。

## 2. 1.0 的定义与范围

### 2.1 定义

**1.0 的标准：能交给陌生人用，不会因为明显缺陷被劝退。**

不是"功能齐"，而是：第一次打开知道该干什么、练到一半不会丢东西、数据丢了能救回来、知道数据存在哪、出了问题能报出自己是什么版本。

### 2.2 必须完成项（按优先级）

#### P0-1 修掉 5 个已知缺陷（0.5～1 人日）

全部【事实】已在当前 `dist/` 复核仍存在：

| # | 缺陷 | 位置 | 现状与后果 |
|---|---|---|---|
| 1 | 超时降级重渲染丢已输入答案 | `app.js:2433`（听音卡输入框无 `value` 回填）；`app.js:2611` 已把值存进 `card.recallTyped` | 弱网进听音卡开始打字，5 秒超时整块重绘，字被清空、焦点丢失。用户第一轮就遇到"白打" |
| 2 | 坏音频护栏用裸 key | `app.js:466` `AUDIO_BROKEN.has(key)`；写入侧是 `audioBrokenKey(key)`（`v:key`，见 311/319 行） | 判断恒为 false，已标记坏的词在非听音入口仍反复拉分片、反复弹失败提示，看起来像"应用坏了" |
| 3 | 两句过期文案 | `app.js:3442`、`index.html:243` 写"其余用系统朗读"（代码已彻底不用 TTS）；`app.js:1443` 写"选项会相应减少"（实际是转输入题） | 承诺与行为相反。用户导入后等着听发音，结果什么都没有 |
| 4 | 桌面输入框被 16px 放大 | `styles.css:345-348` 基础规则 16px 全局生效；`styles.css:2218` 注释仍写"桌面窄窗口不跟" | 桌面上输入框比其它控件大两号，第一眼像样式没做完；注释与行为不符，后续维护会踩坑 |
| 5 | 统计计入已屏蔽/已剔除词 | `app.js:2671`（到期数直接数 `srsMap`）、`app.js:2672`（错题数直接取 `wrongBook.length`）、`app.js:3442` 导入统计也不排除 `isHiddenWord` | 完成页数字与实际会出现的词不一致。数据一旦对不上，用户对全部统计失去信任 |

**为什么不做就不能发**：前两条是"用户可见的坏行为"，第三、四条是"承诺不一致 / 观感未完成"，第五条是"数据可信度"。五条加起来不到 1 人日，却直接决定第一印象。

> 落地时顺带处理两条同批低成本项（不单独列项）：`app.js:4198` 附近 Esc 退出筛选弹窗未复位 `sessionEditing`；`styles.css:1824` `var(--text)` 应为 `var(--ink)`。

#### P0-2 数据备份 / 导出 / 恢复（1.5～2.5 人日）

【事实】现状：只能导出，不能导入；导出不含 `userWords` 和 `blocked`；按钮在"进度"页，文案是给作者看反馈。

**必须做的**：
- 导出补全：`userWords`、`blocked`（顺序 + 名单）、完整 `settings`、`srs`、`wrongBook`、`daily`、`stats`，带 `schemaVersion` 与导出时间。
- 新增「导入恢复」：校验 `app: 'word-desk'` 与 `schemaVersion`，按单词合并（同词取较新的 `lastReview`），导入前预览"将恢复 N 个词条 / M 条复习记录"，二次确认后写入并重载。
- 文案改成"备份 / 恢复"，并在首次导出时提示"这份文件是唯一的进度副本，请自己保存"。

**为什么不做就不能发**：全部数据在本机 IndexedDB，清缓存、换浏览器、换手机即归零。用户丢一次进度就再也不会回来，且作者拿不到任何补偿手段（没有账号可查）。备份是唯一可交付的"后悔药"。

#### P0-3 首次使用引导（1～1.5 人日）

【事实】现状零引导。第一次打开是"0/10/0/0"四格 + 「今日复习计划（10 词）」按钮；而这时用户没有任何复习历史，标题与按钮都在说"复习"。

**必须做的**：
- 一次性引导（可跳过，`localStorage` 记已看过）：一屏讲清三件事——① 这里不是词典，是"选词 → 拆解/猜义 → 验证 → 拼写"的练习；② 可以按前后缀筛词再练；③ 数据只存这台设备、怎么备份。
- 首次（`srsMap` 为空且无自建词）把主按钮文案从"今日复习计划（10 词）"改成"用 10 个新词试一轮"，并在四格统计旁加一句"今天还没有复习记录"。
- 首轮卡片上保留阶段名（已有"第 1 步"），补一句每步要做什么。

**为什么不做就不能发**：产品的核心差异化（筛词 + 四阶段）在界面上没有任何解释，陌生人会把它当"背单词/查词"工具，用两分钟就关掉。引导是 1 人日的转化杠杆。

#### P0-4 隐私与数据说明（1～1.5 人日）

【事实】现状：footer 一行"数据保存在当前浏览器"；埋点面板写"只存在本机，默认不上传"；没有独立说明页，没有"清除全部数据"。

**必须做的**：
- 一页"数据与隐私"（从 footer / 设置进入），回答四个问题：存了什么（词条、SRS、错题、埋点事件）、存在哪（本机 IndexedDB）、会不会上传（默认不上传；只有用户自己填端点并开启才会 POST）、怎么删（一键清除 + 浏览器面板路径）。
- 新增「清除本机全部数据」：二次确认，清 `wtp.db.v3`、`wtp.ls.*`、`wd-theme`、`AUDIO_BROKEN`、音频缓存，保留内置词库，清完回到空库。
- 埋点说明里注明事件内容（`app_open` / `practice_start` / 练习事件等）与保留上限（`maxEvents=1200`）。

**为什么不做就不能发**：应用会往浏览器存学习记录和自建词，"数据在本地"目前只是一句 footer。陌生用户（尤其被朋友转发的）会先问"我的东西去哪了"，答不上来就不敢用。

#### P0-5 错误与空态（1～1.5 人日）

【事实】现状：筛选 0 命中、词库 0 词、错题本为空都有空态按钮（可用）；导入错误最多列 8 条 + 剩余计数；音频失败在卡上降级（可用）。缺口在三处：
- IndexedDB 打开失败降级 localStorage/内存时，界面没有任何提示，用户以为已保存。
- 首次访问且网络失败时没有离线外壳，白屏且无说明。
- 初始化抛错只在 body 末尾贴一张浮动卡片，没有"重试 / 以只读模式继续"。

**必须做的**：
- IndexedDB 降级时顶部常驻一条提示："当前浏览器禁用了本地数据库，本次练习记录不会保存"。
- 首屏加载失败给可操作页：说明需要联网加载一次、提供"重试"，并说明之后可离线使用。
- 初始化失败卡片补版本号 + 复制错误信息按钮。

**为什么不做就不能发**：这三条是"用户会以为数据存住了、其实没有"的沉默失败，比报错更伤。

#### P0-6 发布与版本更新机制（1～1.5 人日）

【事实】现状：`sw.js` `CACHE='wtp-shell-v47'`，install 时 `skipWaiting()`、activate 时 `clients.claim()`；页面/`app.js`/`styles.css` 网络优先；无"新版本可用"提示；footer 版本号是硬编码 `V0.09`；`CONFIG.version=2026.11.05.2` 只在埋点里；版本号递增靠 `AGENTS.md` 里的人工规则。

**必须做的**：
- 版本单一来源：footer 显示 `CONFIG.version`，并在"数据与隐私"页显示 SW 缓存版本，出问题时可让用户报数。
- 更新提示：监听 `navigator.serviceWorker.controllerchange`（或注册后比对 `sw.js` 的缓存名），出现"有新版本，点此刷新"；不自动刷新，避免打断正在做的题。
- 发布检查清单固化成文档步骤：递增 `wtp-shell-vNN` → 确认 `content/sensitive.json` 在提交里 → 发布后强刷两次验证 → 抽查 `audio/index.json` 的 `v` 与分片是否同批。
- 发布前跑 `node --check dist/app.js && node --check dist/sw.js`。

**为什么不做就不能发**：已打开的页面会一直跑旧 `app.js`，用户报问题时你无法确认版本；手动递增漏一次，用户就永久停在旧缓存。这是"能不能持续发版"的地基，不是锦上添花。

#### P1-1 发布前回归清单（1～1.5 人日）

【事实】`交接清单-20261105.md` 写明：测试套件在另一棵树（`temp_20261103_04/word-desk/.test/`），且 `ROOT` 指向旧树根部，**不是本仓库的 `dist/`**，直接跑会大面积失败；本仓库没有 CI。

**必须做的**：一份 20 条以内的手工冒烟清单（首页可点、三种方向各一轮、导入 6 入口各一次、屏蔽与撤销、导出/恢复、断网重开、390px、iOS 聚焦不缩放、Console 无 error），每次发布照做，结果记在提交说明里。

**为什么放在 P1**：它不阻塞首次可用，但决定"每次发版会不会引入回归"。若 1.0 只发一次，可合并进 P0-6 的发布检查。

### 2.3 1.0 明确不做

| # | 不做 | 延后理由 |
|---|---|---|
| 1 | 账号与多设备同步 | 需要后端、鉴权、冲突合并与运维；1.0 的失败点不在同步，导出/恢复已能兜底换机 |
| 2 | 换成真正的 FSRS / ts-fsrs | 换算法需要真实复习数据做对照，现在一条留存数据都没有；先有数据再谈算法 |
| 3 | 词根数据补齐（119 → 数百词） | 主要成本是人工校验切分，不是写代码；且专项入口目前隐藏，先修入口再谈内容 |
| 4 | 例句 / 搭配 / 同义词 | 需要新数据源与版权确认，会把词卡信息密度翻倍；1.0 先控体积与认知负担 |
| 5 | 发音评分 / 跟读自评 | `FEATURES.followRead=false` 已下架，依赖标准发音与 ASR，风险高且非核心闭环 |
| 6 | 分享词表 / 课程 / 班级 | 平台化能力，前置是账号体系，与第 1 条同批 |
| 7 | 付费 | 无账号、无差异化的付费内容，收款与售后是单人无法承担的额外负担 |
| 8 | 词库扩到 ECDICT 全量（77 万行）/ 原生 App 打包 | 前者体积与质量筛选成本高、练习体验被长尾词稀释；后者 PWA 已可安装，投入产出比低 |

## 3. 2.0 的方向选择

三条路线互斥（选一条做主线，其余最多做极小的支撑项）。

### A. 内容深度路线

- **解决什么问题**：词量天花板、词根专项不可用、词条信息太薄（无例句/搭配/同义）、自建词没发音。
- **前置条件**：ECDICT 全量与分级口径（按考试标签/词频切分为"核心 3000 / 进阶 6000 / 全量"）；词根切分数据（需要人工校验，机器切分误报率高）；例句/搭配数据源与许可；自建词音频方案（TTS 生成还是录音）与体积预算。
- **工作量**：最小可交付 8～12 人日（分级抽词 2～4、词根补到 300～500 词 8～15、自建词音频管线 3～5）；完整版 25 人日以上。
- **最可能死在哪**：词根与例句是线性人力活，做到一半数据质量参差，"专项训练"仍只有少数词根可用，投入越大越难停、也越难回滚。

### B. 学习效果路线

- **解决什么问题**：复习算法不可信、错题没有闭环、学完不知道有没有进步、没有回来练的理由。
- **前置条件**：至少 2～4 周真实复习数据（用于对照新算法）；1.0 已补上导出/恢复与本地埋点；明确的对照指标（每日正确率、30 天留存、人均周练习次数）。
- **工作量**：8～15 人日（`ts-fsrs` 接入 2～3、老数据迁移与回归 2～3、错题闭环 2、学习报告 3～4、每日目标与提醒 2～3）。
- **最可能死在哪**：算法换了，却拿不出任何指标证明变好；用户感知不到差异，迁移反而打乱老进度，"优化"变成负收益。

### C. 平台化路线

- **解决什么问题**：多设备、分享词表/课程、班级小组、付费。
- **前置条件**：账号体系 + 后端 + 数据合规（隐私政策、注销与导出）+ 运维（备份、监控、告警）。当前没有后端、没有自有域名（Qoder 托管）、单人维护。
- **工作量**：30～55 人日（账号与同步 15～25、分享/班级 10～20、付费 5～10），不含合规成本与长期运维。
- **最可能死在哪**：两端离线各练了一批词，同步时同一个词的 `stability`/`due` 要合并，没有同步协议与冲突策略就会丢进度或重复复习，而且一旦丢数据就要对用户负责。

### 推荐：B

1. **当前最大的不确定性不是词量，是"有没有人第二周还回来"**。3400 词 + 100% 离线音频已经过了"够不够练"的门槛；留存暂无数据，需先埋点观察。B 里成本最低的几项（学习报告、错题闭环、每日目标提醒）恰好是能把留存从"看不见"变成"可观测"的手段。
2. **B 的前置正好由 1.0 补齐**，边际成本最低：1.0 的导出/恢复提供真实复习数据，埋点提供行为数据；A 是线性人力投入，C 需要后端与长期运维，在数据为零时做，失败概率都会被放大。
3. **单人维护的可持续性**：B 的改动集中在调度层与几个视图，可灰度、可回滚；C 一旦上线就要对账号、丢数据、退款负责，维护成本与风险都是最高的一档。

**被放弃路线在什么条件下值得重新考虑**（【判断】，数字为经验值，需按实际数据校准）：
- **A 重启条件**：观察期内出现内容信号——① 有相当比例的用户导入自建词（例如 ≥30% 用户导入 ≥20 词）；② 反复收到"词不够 / 没有例句 / 词根专项在哪"的反馈；③ 决定主打某个考试（四六级/雅思）需要分级词表。满足任一条，优先做 A 的最小版（分级词库 + 修好词根专项入口），不做全量。
- **C 重启条件**：① 4 周留存稳定在 ≥20%，且人均周练习 ≥3 次；② 出现 ≥3 例"换设备就丢进度"的真实抱怨；③ 出现明确的付费群体（班级、机构、家长代管）。三条同时满足才评估 C 的极简版（先做跨设备导出/导入 + 轻量账号），仍不做班级与付费。

## 4. 时间线（粗粒度）

```
1.0 收尾（2～4 周）→ 观察期（4～8 周）→ 2.0 立项（1 周内定稿，8～15 人日，2～3 个迭代）
```

### 阶段 1：1.0 收尾（约 2～4 周）

- 范围：第 2 节 P0-1 ～ P0-6，P1-1 合并进发布检查。
- **判断点**：2.4 的 16 条验收全绿，才发给"朋友以外的陌生人"；任何一条未过，不进观察期。
- 发布节奏建议：P0-1 + P0-2 先发一版（修坏行为 + 给后悔药），再发引导/隐私/版本三件套。

### 阶段 2：观察期（4～8 周）

- 对象：当前只有 1～2 位外部用户来问（【事实】），样本不足；建议扩到 5～10 位陌生用户（经验值：低于 5 人看不出趋势，高于 10 人单人维护不过来）。
- 需要先补的埋点：`app_open` 已有；补 `session_finish`（完成/放弃、题数、正确率）、`day_return`（次日回访）、`export_click`、`import_click`、`onboarding_done`。留存数据**【暂无数据，需先埋点观察】**。
- **判断点**（数字均为经验值，需按实际数据校准）：
  - 4 周后周活跃 < 3 人且无人主动反馈 → 停在 1.0 修可用性，**不立项 2.0**。
  - 次日留存 < 30% 或 4 周留存 < 10% → 2.0 只做 B 的"报告 + 提醒 + 错题闭环"，**不做算法迁移**（迁移的收益无法被感知）。
  - 4 周留存 ≥ 20% 且人均周练习 ≥ 3 次 → 可做 B 全量（含 `ts-fsrs`），并开始评估 C 的极简版。
  - 导入自建词的用户占比 ≥ 30% → A 的最小版（分级 + 词根入口）排到 B 之前。
  - 出现 ≥3 例"换设备丢进度" → 先做 C 的跨设备导出/导入（不做账号）。

### 阶段 3：2.0 立项（观察期结束后 1 周内）

- 只选一条路线，冻结范围；B 拆 2～3 个迭代：① 错题闭环 + 学习报告；② `ts-fsrs` 迁移（带旧数据兼容与回滚开关）；③ 每日目标与提醒。
- **判断点**：第一个迭代发布后 2 周，若人均周练习次数没有上升（经验值：≥10% 相对提升才算有信号），停止后续迭代，回到 1.0 维护模式。

## 5. 风险清单

1. **内容版权（中高）**【判断】
   `words-core.js` 注明来源是 ECDICT 快照（77 万行）。ECDICT 仓库是 MIT，但其词条释义综合了多部词典与网络数据，**代码许可不一定覆盖数据再分发**。当前免费、无广告、无付费时风险较低；一旦收费或做课程分发，必须先核对 LICENSE、保留出处/NOTICE，并确认释义可否再分发。

2. **音频包体积增长（中）**【事实 + 判断】
   现状 3400 词约 14.6 MB / 17 分片。按同比例扩到 1 万词约 40 MB 以上，Qoder 静态托管的同步耗时、首播命中率与移动端流量都会变差；自建词目前没有音频，若给自建词也生成音频，体积会随用户行为增长且不可预估。

3. **用户数据只在本机导致的流失（高）**【事实】
   没有账号、没有云同步，`userWords` / `srs` / `wrongBook` 全在本机 IndexedDB。清缓存、换浏览器、换手机即归零；1.0 补了导出/恢复，但**用户不会主动备份**。这类流失无法挽回，也无法通过后端数据做任何召回。

4. **单人维护的可持续性（高）**【事实】
   本仓库没有 CI、没有可用测试（测试套件在另一棵树且基准是旧代码），SW 版本靠人工递增，发布靠手动同步 git；已经发生过 `sensitive.json` 未入库、`AGENTS.md` 版本号过期、审查报告说"已修"但实际未生效的情况。任何一次遗漏都可能直接上线残缺版本。

5. **功能越加越重的产品漂移（中高）**【事实 + 判断】
   现状已有 3 个视图、3 种方向、4 个阶段、6 个导入入口、埋点设置、音频缓存管理、屏蔽与撤销。继续加账号/班级/付费，会把"按词缀筛词练习"这个原点稀释成通用学习 App，单人既维护不动、也说不清它是什么。

6. **敏感词治理的漏网与误伤（中）**【事实】
   治理依赖"词头精确清单 + 释义正则 + 人工复核"（29 标记 / 5 剔除）。新增来源（自建词、远端 `words-extra.json`、粘贴词表）不走人工复核；导入统计仍把隐藏词计入（P0-1 第 5 条），用户会看到"导入成功 N 条"但词库里没有。

7. **内容热更新与离线缓存的一致性（中）**【事实】
   `manifest.json` 版本 + 网络优先 + 失败静默回退内置副本；远端内容坏掉时用户无感知。音频侧 `index.json` 的 `v` 必须与分片同批重建，护栏目前只有一半生效（P0-1 第 2 条）。这两处都属于"静默错误"，出问题时最难定位。

8. **算法可信度（中）**【判断】
   自实现 FSRS 的参数全部硬编码、未用真实数据拟合，`desiredRetention=0.9` 只是目标值而非实测值。若用户发现"总在复习同一批词"或"明明记得却一直出现"，会直接怀疑整个复习计划；这也是 2.0 选 B 而不是继续加内容的原因之一。
